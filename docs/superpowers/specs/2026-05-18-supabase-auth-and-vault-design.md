# Supabase Auth + Multi-Notebook Vault — Design

**Date:** 2026-05-18
**Status:** Design approved (wireframe reviewed and accepted), ready for implementation planning
**Branch:** `feat/supabase-auth-and-vault`
**Wireframe:** `/Users/trinabgoswamy/Documents/New project/wireframes/lumen-vault-wireframe.html`

## 1. Goal

Turn Lumen from a single-device, single-vault tool into a per-user, multi-notebook
product backed by Supabase. Users sign up, sign in, and own a private collection
of notebooks — each notebook is one journaling session, with its own entries,
entities, and relations. A new root `/vault` page renders the union of all the
user's notebooks as an in-app Obsidian-style vault: file-tree sidebar, master
knowledge graph with temporal highlight, and a markdown note pane that can be
swiped up to fully cover the graph. The downloadable Obsidian export remains
1:1 with what `/vault` renders.

## 2. Scope

### In scope

- Supabase Auth: email + password and magic-link sign-in. Sign-up, sign-in,
  sign-out, password reset, session refresh, SSR-aware session reads.
- Postgres schema for `profiles`, `notebooks`, `journal_entries`, `entities`,
  `relations`, `follow_ups`, `asked_questions` — all with `user_id`-scoped
  Row-Level Security.
- Migration of the existing browser-local `lumen.journal.v1` blob into
  per-user Postgres rows on first login. Auto-split into session-notebooks
  by 30-minute `createdAt` gaps. AI-title each session via Groq.
- New routes:
  - `/auth/login`, `/auth/signup` — Supabase auth screens.
  - `/dashboard` — welcome hero + time-grouped grid of notebook cards.
  - `/vault` — master view: sidebar + master graph + note pane with the
    vertical-split, drag-to-expand interaction.
  - `/notebook/[id]` — per-session Lumen (visually identical to today's
    `/app`, just scoped to one notebook and reading from Supabase).
- Master graph: react-force-graph-2d over the union of all notebooks'
  entities, with visualize-only entity merging by `slugify(name)` and a
  temporal-highlight overlay reactive to sidebar hover / selection.
- Obsidian-style markdown rendering pipeline for the note pane: remark +
  rehype + custom `remark-wiki-link` plugin. Wikilinks resolve in-app to
  vault notes; same syntax exports as functional Obsidian links.
- Refactor of `src/lib/obsidian-export.ts` so a single markdown generator
  feeds both the in-app vault index and the zipped download — the
  export-equals-render guarantee.
- Update the two existing Supabase edge functions (`extract-graph`,
  `speak-agent`) to flip `verify_jwt = true` and scope writes to the
  authenticated user's active notebook.

### Out of scope

- Free-form note authoring. The vault is read-only — content is generated by
  the voice→Groq extractor. Users edit by speaking, not by typing. A
  later iteration can add an "append-a-note" affordance per page.
- Workspace / shared / collaborative tenancy. Strictly per-user for v1.
  Schema is shaped so a `notebook_collaborators` join table can be added
  later without a breaking migration.
- Real-time collaboration (Y.js / CRDT). Not needed under per-user-only.
- Cross-device sync conflict resolution. Last-write-wins is fine for v1 —
  a user typically journals from one device at a time.
- iOS app changes. The "Available on iOS — spring 2026" copy on the
  landing page is unaffected by this work.
- New Obsidian-renderer features beyond the core set listed in §11.
  Callouts (`> [!note]`), embedded notes (`![[X]]`), math, and Mermaid
  are explicitly deferred.
- Auto-segmentation heuristics beyond a 30-minute gap during migration.
  No NLP / topic-modeling — gaps in time are the only signal.
- Mobile-optimized `/vault` layout. Vault is desktop-first in v1; mobile
  gets a sheet/drawer pattern in a follow-up.

## 3. Background — what changes vs. today

Lumen today stores one `JournalState` blob per device in `localStorage` at
key `lumen.journal.v1`. The blob holds every entry, entity, relation,
follow-up, and asked-question the user has ever produced on that device.
There is no user account; the BYOK Gemini API key (`lumen.gemini_api_key`)
is the only gate to `/app`. The vault is materialized only on export, by
`src/lib/obsidian-export.ts` writing markdown into a `Lumen Vault.zip`.

Three things change:

1. **Identity moves from device to user.** Supabase Auth supplies a
   stable `auth.uid()` per signed-in user. All data tables are scoped to
   that uid via RLS. The BYOK Gemini key stays in `localStorage` —
   different concern (talking to Gemini ≠ identifying yourself to
   Lumen), and keeping it local-only preserves the existing trust model.

2. **The vault becomes multi-notebook.** Each journaling *session*
   (capture-to-stop) becomes its own notebook (Reading A from
   brainstorming). The dashboard is a wall of those session-notebooks;
   the master vault aggregates entities across them.

3. **The vault becomes browsable in-app.** Today the vault only exists
   as a downloadable ZIP. `/vault` is the in-app rendering of that same
   structure, with one drag-to-expand interaction (graph collapses,
   note pane fills the right side) to switch between *ambient context*
   reading and *focused* reading.

## 5. Data model

All `public.*` tables carry a `user_id uuid not null references auth.users(id)
on delete cascade`. RLS policy on each, mirroring this template:

```sql
alter table public.<name> enable row level security;

create policy "owner select" on public.<name>
  for select using (auth.uid() = user_id);

create policy "owner insert" on public.<name>
  for insert with check (auth.uid() = user_id);

create policy "owner update" on public.<name>
  for update using (auth.uid() = user_id)
            with check (auth.uid() = user_id);

create policy "owner delete" on public.<name>
  for delete using (auth.uid() = user_id);
```

### Tables

```sql
create table public.profiles (
  user_id     uuid primary key references auth.users(id) on delete cascade,
  display_name text,
  created_at  timestamptz not null default now()
);

create table public.notebooks (
  id          uuid primary key default gen_random_uuid(),
  user_id     uuid not null references auth.users(id) on delete cascade,
  title       text not null,                  -- AI-titled or "Untitled Session"
  title_source text not null default 'ai',    -- 'ai' | 'user' | 'auto'
  started_at  timestamptz not null,           -- session start (first entry)
  ended_at    timestamptz,                    -- session end (last entry)
  duration_seconds integer,                   -- denormalised for sort/filter
  entity_count integer not null default 0,    -- denormalised for cards
  summary     text,                           -- AI summary, 1-2 sentences
  archived_at timestamptz,                    -- soft archive (kept in DB)
  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now()
);
create index on public.notebooks (user_id, started_at desc);

create table public.journal_entries (
  id          uuid primary key default gen_random_uuid(),
  user_id     uuid not null references auth.users(id) on delete cascade,
  notebook_id uuid not null references public.notebooks(id) on delete cascade,
  text        text not null,
  created_at  timestamptz not null            -- the *moment* spoken
);
create index on public.journal_entries (notebook_id, created_at);

create table public.entities (
  id          text not null,                  -- slug, e.g. 'maya'
  user_id     uuid not null references auth.users(id) on delete cascade,
  notebook_id uuid not null references public.notebooks(id) on delete cascade,
  name        text not null,
  type        text not null,                  -- person | place | concept | …
  description text,
  metadata    jsonb not null default '{}'::jsonb,
  mentions    integer not null default 1,
  first_seen  timestamptz not null,
  last_seen   timestamptz not null,
  questions   text[],
  primary key (notebook_id, id)
);
create index on public.entities (user_id, name);   -- master-graph lookup

create table public.relations (
  id            text not null,                -- "src__label__tgt"
  user_id       uuid not null references auth.users(id) on delete cascade,
  notebook_id   uuid not null references public.notebooks(id) on delete cascade,
  source_id     text not null,
  target_id     text not null,
  label         text not null,
  metadata      jsonb not null default '{}'::jsonb,
  created_at    timestamptz not null default now(),
  superseded_at timestamptz,                  -- soft-superseded (audit)
  primary key (notebook_id, id)
);
create index on public.relations (notebook_id) where superseded_at is null;

create table public.follow_ups (
  id            uuid primary key default gen_random_uuid(),
  user_id       uuid not null references auth.users(id) on delete cascade,
  notebook_id   uuid not null references public.notebooks(id) on delete cascade,
  question      text not null,
  reason        text not null default '',
  target_entity_ids text[] not null default '{}'::text[],
  answered      boolean not null default false,
  created_at    timestamptz not null default now()
);

create table public.asked_questions (
  id            uuid primary key default gen_random_uuid(),
  user_id       uuid not null references auth.users(id) on delete cascade,
  notebook_id   uuid not null references public.notebooks(id) on delete cascade,
  question      text not null,
  target_entity_ids text[] not null default '{}'::text[],
  asked_at      timestamptz not null default now()
);
create index on public.asked_questions (notebook_id, asked_at desc);
```

### Why notebook-scoped entities, not user-scoped

Reading A makes each session-notebook a discrete artifact — the same name
"Maya" in different sessions might or might not refer to the same person.
Storing entities at the notebook level preserves that ambiguity in the
data. The master graph (§12) does a visualize-only merge across notebooks
for the UI without changing the canonical storage. A future feature can
promote selected entities to user-scope when the user explicitly says
"this is the same Maya"; that's a smaller migration than the reverse
direction.

### Profile auto-create

Use a Supabase database trigger so `public.profiles` rows are inserted
automatically on `auth.users` insert:

```sql
create or replace function public.handle_new_user() returns trigger
language plpgsql security definer set search_path = '' as $$
begin
  insert into public.profiles (user_id, display_name)
  values (new.id, new.raw_user_meta_data->>'display_name');
  return new;
end;
$$;
create trigger on_auth_user_created
  after insert on auth.users
  for each row execute procedure public.handle_new_user();
```

## 6. Authentication

### Provider & flow

- **Email + password.** Default. Verification email enforced.
- **Magic link.** Single-tap sign-in from email; cuts re-engagement
  friction. Useful since journaling is a "come back next week" product.
- **No social OAuth in v1.** Adds setup overhead and account-linking
  complexity that doesn't pay off until usage justifies it.

### SSR session bridge

TanStack Start renders server-side. Sessions live in HTTP-only cookies,
read on both the server (during SSR data loaders) and the browser:

```ts
// src/lib/supabase/server.ts
import { createServerClient } from "@supabase/ssr";

export const getServerSupabase = (req: Request) =>
  createServerClient(SUPABASE_URL, SUPABASE_ANON_KEY, {
    cookies: { /* read/write from req/response */ },
  });
```

```ts
// src/lib/supabase/browser.ts
import { createBrowserClient } from "@supabase/ssr";

export const supabase = createBrowserClient(SUPABASE_URL, SUPABASE_ANON_KEY);
```

### Route gating

- `/dashboard`, `/vault`, `/notebook/[id]` require an authenticated
  session. Server loader returns `redirect("/auth/login")` if absent.
- `/auth/login`, `/auth/signup`, `/auth/callback`, `/`, `/welcome` are
  public.

### Relationship to the existing BYOK Gemini gate

The `/welcome` BYOK gate stays exactly as it is — it gates *talking to
Gemini* for live transcription, which is a different concern from
*identifying yourself to Lumen*. The order is:

```
Anonymous → /auth/login → authenticated → /welcome (if no Gemini key)
                                       ↓
                                   /dashboard
```

The Gemini key remains in `localStorage` per-device. Future
improvement (out of scope): allow the user to encrypt-and-stash it
into their profile so they don't re-enter it across devices.

## 7. Notebook model

### Lifecycle

1. **Created** when the user starts a new recording session from
   `/dashboard` ("Start a new session" button) or directly from the
   nav. Notebook row inserts immediately with `title = "Untitled
   Session"`, `title_source = "auto"`, `started_at = now()`.
2. **Active** as long as the user is recording / speaking. Entries
   stream into `journal_entries`; the extractor edge function (now
   auth-scoped) writes entities/relations as they're produced.
3. **Ended** when the user stops recording. `ended_at` and
   `duration_seconds` set. AI titler is invoked: a Groq call summarises
   the transcript into a ≤6-word title and a ≤2-sentence summary.
   `title`, `summary`, `title_source = "ai"` updated.
4. **Visible on `/dashboard`** under the appropriate time bucket (Today
   / This week / This month / Earlier).
5. **Archivable.** `archived_at` set hides from dashboard default view
   but keeps the row queryable and exportable.

### Naming

- Default: AI-generated 4–6 words from the transcript via Groq, then
  slug-safe. Example: `"CS246 cram session"` → file slug
  `22-30_cs246-cram-session`.
- User override: rename inline on the notebook card or in the notebook
  header. Sets `title_source = "user"` so subsequent re-extractions
  don't overwrite it.
- Fallback: if Groq fails or the transcript is too short, use
  `"HH:MM Session"` with `title_source = "auto"`.

### Granularity decision (reference only)

Reading A from brainstorming: one notebook per session, not per theme.
Captured here because it changes how the dashboard is paginated and how
the master graph performs at scale (see §16).

## 8. The `/vault` page

The new primary read-surface. See wireframe at the path in this doc's
header for the canonical visual reference.

### Layout

Three regions in a two-column shell:

```
┌────────────────┬──────────────────────────────────┐
│  Sidebar       │   Pane header (title + actions)  │
│  (entities,    ├──────────────────────────────────┤
│   Sessions/,   │                                  │
│   README)      │   Graph pane (top)               │
│                │   — master force graph           │
│                │   — temporal highlight overlay   │
│                ├══════════════════════════════════┤  ← drag handle
│                │   Note pane (bottom)             │
│                │   — Obsidian-style render        │
│                │   — file-path strip + Export     │
└────────────────┴──────────────────────────────────┘
```

- Left column: 296px fixed.
- Right column: two stacked panes, default 50/50 split.
- Drag the handle upward → graph height shrinks live; opacity drops
  below ~40px of remaining graph height for a soft fade. On release,
  snap thresholds apply: graph height < 80px → fully collapsed (note
  pane flexes to fill); graph height > 85% of available → fully
  expanded (note pane minimised to the strip + handle). Drag back
  down → restored. Keyboard shortcut `⌘E` toggles between
  50/50 and fully-expanded states.
- Use `react-resizable-panels` for the split (already installed) with
  the snap thresholds wired via its `onLayout` callback.

### Sidebar (`components/vault/sidebar.tsx`)

- Header: Lumen wordmark, `"Vault — {display_name}"` crumb, search input.
- **README** section: single `Map of Content` link → renders the
  user-level README.
- **Entities** section: every entity across the user's notebooks,
  visualize-merged by `slugify(name)`, sorted by aggregate mention count
  desc. Glyph color reflects type (amber=person, sage=place, ink=concept).
- **Sessions** section: grouped by date (descending), each date a folder
  header; sessions inside it ordered by time, labelled
  `HH:MM · {notebook.title}`.
- Hovering any item or any date-folder fires `applyHighlight({day})` /
  `applyHighlight({nodeIds})` on the graph — see §12.
- Clicking sets the active note in the note pane and pins the highlight.

### Master graph pane (`components/vault/graph.tsx`)

- `react-force-graph-2d` with custom `nodeColor`, `linkColor`, and
  `nodeCanvasObject` to render the Lumen aesthetic (small filled
  circles, type-coded, with soft halo).
- Data: union of all entities/relations across the user's notebooks,
  merged by `slugify(name)` for nodes; edges deduplicated by
  `(source, label, target)`.
- Temporal highlight: `nodeOpacity` and `linkColor` accessors driven by
  the current "highlight set" — a `Set<entityId>` derived from the
  current hover or selection. Dim state is opacity 0.18; lit is
  default. Transitions are 380ms cubic-bezier-eased via `motion`.

### Note pane (`components/vault/note-pane.tsx`)

- Drag-handle at top, then file-path strip (`Vault / Maya.md` + Export),
  then a scrolling container that renders the active note through the
  Obsidian pipeline (§11).
- Read-only. No edit cursor, no toolbar.
- Wikilinks (`<a class="wikilink" data-target="…">`) call
  `setActiveNote(slug)` rather than navigating.

### Empty states

- No notebooks yet → sidebar collapses, note pane shows a small "Start
  your first session" card linking to `/notebook/new`. Graph hidden.
- Search returns nothing → tree collapses to a centered "Nothing in the
  vault matches '<query>' yet."

## 10. Per-notebook UI (`/notebook/[id]`)

Visually and behaviourally identical to today's `/app`. The diff is the
data source: instead of reading/writing `localStorage` via
`journal-store.ts`, every read becomes a Supabase query scoped to
`(user_id, notebook_id)` and every write is an upsert against the same
row keys.

The dock-pill, entity list, follow-ups, per-notebook graph view, and
recording controls are untouched. Two small UI additions:

- A notebook title field at the top (editable, autosaves; flips
  `title_source` to `"user"` on edit).
- A breadcrumb: `Dashboard › {notebook.title} (HH:MM)` for orientation.

`journal-store.ts` keeps its exported function signatures unchanged so
the consuming components don't need code changes — just a data-layer
swap underneath.

## 11. Obsidian-style markdown rendering

### Pipeline

```
markdown (string)
  → remark-parse
  → remark-gfm                  (tables, task lists)
  → remark-frontmatter          (extract YAML; not rendered as text)
  → remark-wiki-link            (custom; [[X]] → mdast wiki-link node)
  → remark-rehype
  → rehype-react                (with custom components for wiki-link,
                                 callouts-later, etc.)
```

All packages are edge-safe (no `fs`, no `Buffer` reliance). They run in
the Cloudflare Worker runtime as well as in the browser.

### V1 feature set

| Feature | Syntax | Render |
|---|---|---|
| Wikilink | `[[Maya]]` | `<a class="wikilink" data-target="maya">Maya</a>` |
| Aliased wikilink | `[[Maya\|her]]` | text = "her", target = "maya" |
| Anchored wikilink | `[[Sessions/2026-05-17/22:30\|10:30 PM]]` | navigates to session note |
| YAML frontmatter | `--- … ---` | extracted; rendered in a quiet sidebar callout |
| Tags | `#person #cs246` | hashtag pill; click filters sidebar |
| Task-list | `- [ ] question` | unchecked checkbox in amber |
| Standard markdown | h1-h6, b, i, ul/ol, blockquote, code, tables | as Obsidian |

### V1 deferred

Callouts (`> [!note]`), embedded notes (`![[X]]`), math, Mermaid. Tracked
in §17.

### Wikilink resolution

The custom `remark-wiki-link` plugin emits a `wikiLink` mdast node with
`{ value: "Maya", alias: "her" | undefined, anchor: "22:30" | undefined }`.
`rehype-react` maps it to a React component that:

1. Looks the target up in the in-memory vault index (see §13).
2. If found, renders an `<a class="wikilink" data-target="<slug>">`.
3. If missing, renders a muted `<span class="wikilink-missing">` —
   matches Obsidian's "non-existent link" treatment, signals to the
   user that the extractor created a link to an entity that has since
   been pruned.

A click handler on the parent renders area intercepts `.wikilink`
clicks and calls `setActiveNote(target)` instead of letting the browser
navigate — `/vault` stays on one URL.

## 12. Master graph + temporal highlight

### Data assembly (`lib/vault/graph-data.ts`)

```ts
type MasterGraphData = {
  nodes: { id: string; name: string; type: EntityType;
           mentions: number; days: string[] }[];
  edges: { source: string; target: string; label: string }[];
};

function buildMasterGraph(notebooks: NotebookWithChildren[]): MasterGraphData;
```

- Nodes: group all entities across notebooks by `slugify(name)`. Take
  `name` from the most-recently-mentioned occurrence; sum `mentions`;
  union of `days = notebooks.where(contains entity).map(started_at as
  YYYY-MM-DD)`.
- Edges: deduplicate `(slugify(source), slugify(target), label)` across
  all notebooks; drop edges with `superseded_at` set.

### Highlight state

A single `useState<HighlightState>` in `vault.tsx`:

```ts
type HighlightState =
  | { kind: "all" }
  | { kind: "day"; day: string }
  | { kind: "nodes"; ids: Set<string>; label: string };
```

- Sidebar hover sets a transient state via `onMouseEnter`.
- Sidebar leave snaps back to the *pinned* state derived from the
  active note (clicked, not hovered).
- The graph component consumes `HighlightState` via context, computes
  per-frame `nodeOpacity` / `linkColor` from it, and animates
  transitions via `motion`.

### Memoization

The `days → entityIds` index is precomputed once per data refresh and
held in a ref so per-hover recomputation is O(1). Recomputation is
triggered on notebook-list changes only.

### Hidden when collapsed

When the note pane is expanded to cover the graph, the graph component
unmounts via `react-resizable-panels`' `Panel` `defaultSize=0` +
conditional rendering. No frames painted, no force simulation running.

## 13. Export-equals-render

### Principle

> The in-app `/vault` view and the downloaded ZIP are two renderings
> of the same underlying markdown source. The sidebar tree is the
> file tree. Every note shown in-app is a real `.md` file that ships
> out unchanged when the user clicks Download Vault.

### Implementation

`src/lib/vault/markdown.ts` exports pure generators:

```ts
generateEntityMarkdown(entity, related, mentions): string
generateSessionMarkdown(notebook, entries, byEntityId): string
generateReadmeMarkdown(state): string
buildVaultIndex(state): Map<string, string>   // path → markdown
```

- `src/components/vault/note-pane.tsx` calls `buildVaultIndex` once,
  caches it, then renders the entry for the active path through the
  Obsidian pipeline.
- `src/lib/obsidian-export.ts` calls `buildVaultIndex` and zips its
  entries via `JSZip`. The download is the cached index.

This refactor is small (~50 lines extracted from current
`obsidian-export.ts`) and is the keystone — once it lands, in-app /
ZIP drift becomes architecturally impossible.

### File layout (the vault shape, v2)

```
{User}'s Vault/
  README.md
  {Entity}.md                   ← one per merged entity, at vault root
  Sessions/
    YYYY-MM-DD/
      HH-MM_{slug}.md           ← one per notebook
```

The legacy `Daily/YYYY-MM-DD.md` shape is gone — sessions are now
discrete artifacts. A `--legacy` toggle on the export button preserves
backwards compat for users who've integrated the old shape into their
Obsidian workflow; ships in a follow-up.

## 14. Migration of existing localStorage data

### First-login flow

1. After sign-in, the client checks `localStorage.getItem('lumen.journal.v1')`.
2. If non-empty *and* the user has zero notebooks in Postgres, prompt:
   *"Import your existing local journal? (12 sessions inferred from
   {n} entries spanning {date range}.)"*
3. On accept, POST the blob to the `migrate-legacy` edge function.

### `migrate-legacy` edge function

Logic:

1. Parse `JournalState` from the request body.
2. Sort `entries` by `createdAt` ascending.
3. Walk entries in order; start a new notebook whenever the gap from
   the previous entry's `createdAt` exceeds **30 minutes**. (This is
   the only segmentation heuristic; no NLP, no topic detection.)
4. For each inferred session, collect:
   - Entries with `createdAt` in the session's window.
   - Entities whose `firstSeen` or `lastSeen` falls in the window
     *and* whose id appears in any of the session's entries'
     `entityIds`.
   - Relations whose endpoints exist in the entity set above.
5. Title each session via Groq (4-6 words from concatenated entries).
   Fall back to `"HH:MM Session"` on failure.
6. Insert the notebook + its children in a single transaction.
7. Return `{ notebookCount, entryCount }` so the client can confirm.

The legacy blob is **not** deleted from `localStorage` until the user
confirms the imported data on `/dashboard`. After confirmation, the
blob is cleared. Failed imports can be retried.

### Privacy note

The migration request is authenticated. The blob never leaves the
user's device unless they opt in. The edge function has RLS-enforced
write access only to that user's tables.

## 15. Edge function changes

### Existing functions

Both currently run with `verify_jwt = false`. With auth landing, both
flip to `verify_jwt = true`:

```toml
# supabase/config.toml
[functions.extract-graph]
verify_jwt = true

[functions.speak-agent]
verify_jwt = true

[functions.migrate-legacy]
verify_jwt = true
```

- `extract-graph` now reads `auth.uid()` from the JWT, looks up the
  user's *active* notebook (passed in the request body as `notebookId`,
  validated against `notebooks.user_id = auth.uid()`), and writes
  entities/relations scoped to that `(user_id, notebook_id)`.
- `speak-agent` (the agent voice / Groq follow-up generator) similarly
  scopes its writes.

### New function: `migrate-legacy`

See §14. Standalone, idempotent (running it twice on the same blob
produces the same rows by virtue of slug-based entity ids and
deterministic relation ids — `mergeExtraction`-style dedup).

## 16. Performance considerations

### Master graph at scale

With Reading A producing one notebook per session, a daily user
accumulates ~180 notebooks in six months. Each contributes ~5-30
entities, so the master graph can hit ~1500-2000 nodes within a year.
`react-force-graph-2d` handles ~3000 with reasonable frame rates;
beyond that it starts to chug.

V1 mitigations:

- **Min-mention filter.** Default the master graph to entities with
  ≥ 2 total mentions. Toggle to "show all" in the graph header.
- **Notebook toggle.** A filter chip row at the top of the graph
  shows "All sessions" or specific dates / weeks. Folds the data set
  before handing to react-force-graph-2d.
- **Visualize-only merge.** §5 keeps storage notebook-scoped, so
  there's no migration penalty if we later promote to user-scoped
  entities for better scaling.

### Highlight recomputation

`days → entityIds` index is precomputed; hover changes are O(1) lookup.
The `nodeOpacity` accessor returns `highlightSet.has(node.id) ? 1 :
0.18`, run by react-force-graph-2d per node per frame — cheap.

### Query patterns

- `/dashboard`: `select * from notebooks where user_id = auth.uid()
  and archived_at is null order by started_at desc limit 100`. Index
  on `(user_id, started_at desc)`.
- `/vault` data load: three parallel queries — `notebooks`,
  `entities` join on notebook_id, `relations` join on notebook_id.
  Wrapped in a TanStack Query loader so SSR and CSR share the cache.
- `/notebook/[id]`: one notebook + its children. Subscribe to
  Supabase realtime channel filtered by `notebook_id` so the
  extractor's writes appear without polling.

## 17. Risks and open questions

| Risk | Mitigation |
|---|---|
| **Master graph performance past ~3000 nodes.** | Min-mention filter (§16); promote to user-scoped entities if it becomes a real ceiling. |
| **First-login migration is irreversible from the user's POV.** | Don't clear legacy blob until they confirm import. Surface a "re-run migration" affordance in settings. |
| **30-minute gap heuristic is wrong for some users.** | Show a preview ("12 sessions inferred — looks right?") before committing. Make the gap configurable in v1.1 if signal emerges. |
| **AI titler returns nonsense or PII-laden titles.** | User can rename inline; rename sets `title_source = "user"` so re-extraction never overwrites. |
| **Cookie-based SSR sessions + Cloudflare Workers.** | `@supabase/ssr` supports Workers via its cookie adapter; verify in a spike before committing migration order. |
| **BYOK Gemini key is per-device, but accounts are per-user.** | Stays out of scope for v1. Add encrypted server-side stash in v1.1 if cross-device usage becomes common. |

### Deferred features (post-v1)

- Free-form note appending per page.
- Callouts (`> [!note]`), embedded notes (`![[X]]`), math, Mermaid in
  the renderer.
- Workspace / shared notebooks (`notebook_collaborators` join).
- Cross-device Gemini-key sync via encrypted profile column.
- Mobile-optimized `/vault` (sheet pattern; drag-up gesture preserved).
- Tag pages (clicking a `#tag` opens a filtered view).
- Re-import / re-segment a notebook with a different gap heuristic.
- Auto-summary regeneration on demand.

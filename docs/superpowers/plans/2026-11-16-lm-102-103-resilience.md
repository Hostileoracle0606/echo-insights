- "Design for delay, not loss": every text step is safe to repeat; the phone picks up unfinished work at launch.

- Tests per step: run twice with the same key, get one result and no duplicate; a changed payload under the same key is refused. pgTAP for SQL (`supabase/tests/database`), `flutter test` for Dart, `node --test` in `infra` for Lambdas, Deno for edge functions.

## Task 1: Card and brief: keyed saves and definite reads (SQL + Dart)

Migration `supabase/migrations/20261116000000_card_brief_idempotency.sql`, pgTAP `supabase/tests/database/card_brief_idempotency_test.sql`.

- Add a ledger for card and brief saves, keyed `(notebook_id, source_revision)` for cards and `(user_id, source_notebook_id, source_revision)` for briefs, storing a `payload_hash` (sha256 of the canonical jsonb card / brief, never the payload). Choose between columns on the existing tables (`session_cards.payload_hash`, `session_briefs.payload_hash`) or a small ledger table, whichever keeps the existing pgTAP tests (`session_cards_test.sql`, `session_briefs_test.sql`, `session_card_drafts_test.sql`) green. Backfill must not be needed: a null hash on an old row is treated as "adopt on first match".
- `save_session_card`: second save of the same revision with the same payload hash returns the stored card, `status: 'saved'` (today's behaviour). Same revision with a different payload hash returns `{status:'rejected', code:'keyReused'}` and writes nothing. Stale/newer rules are unchanged.
- `save_session_brief`: same pattern. Same key and hash: `unchanged`. Same key, different hash: `{status:'rejected', code:'keyReused'}`.
  - Note: the card generator may legitimately produce a different card for the same revision on a retry (a model is not deterministic). Ruling: the CLIENT and Lambda must therefore ask first (below) and not regenerate when a card for that revision exists. A refused `keyReused` is a clean, non-alarming outcome the client treats as "already done".
- Definite reads: `get_card_status(p_notebook_id uuid, p_revision bigint) returns jsonb` -> `{status:'present'|'absent'|'stale'|'notFound', cardRevision, currentRevision}`; `get_brief_status(p_notebook_id uuid, p_revision bigint)` the same for the brief. Both owner-scoped, read-only, no card or brief text returned.
- Dart: `lib/services/session_card_service.dart` and `lib/services/session_brief_service.dart` gain `cardStatus(notebookId, revision)` / `briefStatus(...)` wrappers, and `close()` / `requestBrief()` first ask the status and return the stored card / do nothing when it is already `present` at the current revision. They treat `keyReused` as success. Tests in `test/session_card_service_test.dart` and `test/session_brief_service_test.dart` (twice, same key: one model call and one result).
- Also check the close-session Lambda (`infra/lambda/close-session`, `infra/test/`): if it would call the model before the status is known, make it call `get_card_status` first (user's own token) and skip the model call when present. Add an infra test: second close of the same revision makes no model call.

Acceptance: pgTAP covers both saves twice-same-key, changed-payload refusal, and all four statuses for both reads; Dart and infra tests pass; existing card/brief suites still pass.

## Task 7: The five LM-103 acceptance tests

New `test/catch_up_acceptance_test.dart` (fakes for network, clock, journal directory; all pure `flutter test`). Names must start with `LM-103 case N:`.

1. Crash mid-session: a turn is in the journal, not committed. A fresh runner (new objects, simulating relaunch) without opening the notebook commits the turn and then the card follows.
2. Offline at session end: with the network fake failing, end a session; nothing is produced. Network returns (second catch-up, and again via a resume trigger): card and brief are produced exactly once, and a third run does nothing.
3. Force quit (simulator approximation): interrupt the runner mid-plan (cancel after the commit step, before the card); the next launch's catch-up finishes everything exactly once.
4. Vectors lagging: add an entity, search before its vector exists: retrieval answers without error and without naming a missing vector to the user; the next catch-up builds the vector (poke recorded once), a second catch-up does not.
5. Second iPhone: two separate "device" fixtures sharing one fake server. Phone A ends a session (card pending server-side), phone A's local journal holds one more uncommitted turn, then A is dropped. Phone B's catch-up finishes the server-side steps (card, brief) exactly once; phone A's local-only turn never appears on the server. Add a comment that the "turns only in A's journal are lost" copy belongs to LM-89/LM-110 and is not built here.

Acceptance: all five pass; each is deterministic (no real timers or sleeps; inject clock/delay).
